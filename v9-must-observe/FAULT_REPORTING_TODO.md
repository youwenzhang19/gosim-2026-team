# 故障报修判断待办备忘

## 状态

本次 fix3 暂不把“低 scale ⇒ 报修”写入硬编码规则。故障判断依赖 agent/模型调用；当前调用链路正在由另一位协作者修复。修通前，planner 只维护有效质量的数值证据和诊断状态。

范围说明：现有 agent.py 的自动规则报修分支仍按原样保留；此次未增加、重写或禁用。因此“留待 agent 解决”指后续故障推理与架构接入工作，并不代表当前已实现只有模型能触发 report。

## 已确认的问题

- a1/b1/c1 日志中的运维消息解析分别为 45/45、57/57、54/54 失败。
- b1 的第一条交接消息提供了暗号表、凯撒日期位移、唱名数字映射，并给出导星相机故障的中文和 UTC 时间；消息含明文纠错和“平场/镜盖测试不是故障”的反例。
- b1 在故障通知时段前后出现明显质量下降，但低 factor 单独不能区分仪器故障与天气、方向事件或测试停机。
- `clean_e` 需要近期 exact 质量证据和近期饱和 band 证据；严重故障时饱和证据可能不足，因此旧检测器可能返回 `None`。
- 正确报修会恢复后续效率并产生报告奖励；它不是只有独立加分。官方引擎控制测试中，故障修复前后同一曝光 factor 从 0.004 变为 0.4。

## agent 恢复后的输入契约

agent 不应只接收一个 `scale` 数字。建议提交以下结构化证据：

```json
{
  "quality_estimate": 0.42,
  "quality_lower": 0.30,
  "quality_upper": 0.55,
  "quality_status": "bounded|lower_bound_only|stale|heterogeneous",
  "observation_utc": "...",
  "duration_seconds": 900,
  "clean_support": 12,
  "directional_rejections": 4,
  "recent_public_notices": [],
  "recent_operation_facts": [],
  "recent_reports": []
}
```

其中 `quality_estimate` 是有效观测质量，不等于天气质量，也不等于故障概率。`lower_bound_only` 和 `stale` 不应被 agent 当成精确测量。

以上是未来接入契约示例，不是本次已经接到模型的 payload。当前可直接读取 planner.scale_estimator.diagnostics()，字段名为 estimate/lower/upper/status/last_finite_hour/last_result_hour/support/rejected_directional/needs_probe/exposures_retained，另有 unmeasured 和 no_clean_feedback 状态。绝对 UTC 和曝光时长在 scale_dbg 日志中；实现适配时应把相对小时转换成 UTC。None/无新鲜 E 必须表示“证据不足”，不能被解释为“没有故障”。区间是可行倍率的包络，不是经过概率校准的置信区间。

## agent 需要完成的判断

1. **证据时间对齐**：把公告、forecast、observation、operation note 全部转成 UTC；处理跨夜和本地时间。
2. **可信度排序**：工程组明确通知高于传言；更正后的时间高于旧时间；本台站事实高于邻站信息。
3. **类型识别**：区分全天天气、方向性薄云/风、平场/镜盖测试、导星相机等持续硬件故障、地震或其他已知效率事件。
4. **持续性判断**：只有在质量下降与故障时间/方向/持续性相符，且公告排除天气或测试时，才提高故障概率。
5. **报告决策**：同时考虑免费次数、付费误报惩罚、最近一次报告、是否已经修复，以及报告会改变后续观测效率。
6. **可审计输出**：agent 给出报告建议及证据 ID、来源原文、标准化 UTC、推断理由、不确定性和明确的“建议报修/继续收集证据/非故障”状态。执行层只校验时刻、去重、合法动作及预算，不用 scale 阈值替代 agent 做原因判断。若模型置信度尚未校准，应明确标为模型自评，而非事实概率。

## 验收标准

- 在 b1 这类导星相机案例中，能从明文工程通知定位正确 UTC 时刻，在确认故障开始时或随后首次决策机会报修；不得在故障开始前提前报告，否则可能被计误报。
- 在平场/镜盖测试案例中不报修。
- 在邻站雨、未经确认的传言、方向性薄云案例中不误报全局故障。
- 在没有模型调用或消息解析失败时，数值 planner 继续运行，但不伪造“已判断故障”。
- 用带真值的本地卡做报告混淆矩阵，并单独记录报告奖励、修复后科研分、误报惩罚和 REQUIRED 完成率。

额外的成对验收：在完全相同的卡片、天气、目标、随机种子和预算下对比“agent 正常判断”和“禁用报修建议”，保留每次 report 的原始结果；先证明修复后的有效质量恢复，再讨论对总分的贡献。天气单独下降、故障叠加差天气、重复故障、已修复故障、公告更正、跨夜时间、暂时测试停机、无模型响应都应覆盖。

## 与调用修复负责人的交接顺序

1. 对方先验证一个最小请求：HTTP 返回、模型名、权限、响应格式、超时与错误摘要，日志不记录密钥。当前 http_error 不能直接归为密文难解析。
2. 单独验证夜间建议、运维消息等实际调用路径能返回且通过结构验证，不能只证明一个测试接口可访问。
3. 将明文工程通知和密码本原文作为 agent 输入，由 agent 输出带来源的时间事实；再扩展到编码、相对时间、纠错和条件句。此次不要求在数值 planner 中建设规则解码器。
4. 接入质量证据时保留缺失、过期、只有下界等状态，然后进行建议模式回放，检查误报与漏报。
5. 成对模拟验收后才开启 agent 报修建议的执行。旧规则与新建议如何仲裁、去重、关闭，应另开明确变更，避免两个分支重复报修或互相否决。

## 暂不采取的做法

不在 planner 中增加 `if scale < 常数: report`，不把凯撒/摩斯/唱名解码硬编码进 scale estimator，也不把一次低质量曝光作为故障证明。等 agent 调用链路恢复并能稳定解析结构化事实后，再实现和验证上述契约。
